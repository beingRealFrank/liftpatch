Drupal 10 end of life: what to do before December 9, 2026

Drupal 10 stops receiving security releases on December 9, 2026. This page sets out the dates, the three realistic options, the commands for a self-upgrade, and when it makes sense to pay someone. It is written for the person who owns the site and has to decide this month.

The dates that matter

The official schedule is on drupal.org's core release schedule. Read it directly, because dates have moved before. As of this writing:

  • Drupal 10 reaches end of life on December 9, 2026. After that there are no further Drupal 10 releases, including security releases. 10.6 is the last Drupal 10 minor version. The Drop Times covered the announcement, and endoflife.date tracks every branch in one table.
  • Drupal 11.3 and 10.6 lose security support in the same release window (the week of December 7, 2026, when 11.5 and 12.0 are scheduled). That has a practical consequence: if you are going to upgrade, aim for Drupal 11.4 or later, not 11.3. Landing on 11.3 would put you on a branch that ends within weeks of Drupal 10.
  • Drupal 11.4 security support runs into 2027 according to the drupal.org schedule. Some third-party trackers show a different end date for 11.4, so use drupal.org as the source of truth.

Hosting providers have published their own guidance: see Pantheon's end-of-life overview and Acquia's Drupal 10 end-of-life FAQ. If you are on a managed platform, check what your host will do after the date before you decide anything.

What actually happens on December 10

Nothing breaks on the day. Your site keeps running. What changes is the risk profile:

  • New core vulnerabilities are announced and patched for supported branches only. Attackers read those announcements and diff the fix, so the unpatched branch becomes an easier target, not a neutral one.
  • Contributed modules drop Drupal 10 support over the following months. New releases require Drupal 11, so staying on 10 means freezing every module at its last Drupal 10 version.
  • Your hosting provider, insurer, auditor or procurement contract may treat an unsupported CMS as a compliance finding regardless of whether you have been attacked.
  • PHP versions age out underneath you. Drupal 11 needs PHP 8.3 or newer, and running an old Drupal 10 on an old PHP gets harder to justify each quarter.

How to upgrade yourself, step by step

This is the same sequence we use. Run it on a copy of the site, never on production.

1. Get to the last Drupal 10 minor first

Drupal 11 requires you to be on 10.3 or later before you move. Updating to 10.6 first also surfaces breakage while you can still roll back to a known-good state:

composer require drupal/core-recommended:^10.6 drupal/core-composer-scaffold:^10.6 drupal/core-project-message:^10.6 --update-with-all-dependencies
drush updatedb -y && drush cache:rebuild

2. Measure what blocks you

Install Upgrade Status and run it across every enabled module and theme:

composer require --dev drupal/upgrade_status
drush en upgrade_status -y
drush upgrade_status:analyze --all

It reports, per project, whether a Drupal 11 compatible release exists and which deprecated APIs your custom code still calls. You can also paste your composer.lock into the Liftpatch scanner for the same answer with a price attached, without uploading anything. For a single module, check the compatibility atlas.

3. Fix custom code with Rector

Drupal Rector rewrites many deprecated calls automatically. Review the diff before you accept it:

composer require --dev palantirnet/drupal-rector
vendor/bin/rector process web/modules/custom --dry-run
vendor/bin/rector process web/modules/custom

Rector does not catch everything. Expect to fix by hand: removed procedural functions, base themes that left core (Classy, Stable, Seven, Bartik), and jQuery.once usage that should move to core/once.

4. Handle modules that left core

Several core modules became contributed projects in Drupal 11, including Action UI, Book, Forum, Statistics, Tour and Activity Tracker. If your site has any of them enabled, install the contrib replacement while you are still on Drupal 10, and uninstall nothing until the replacement is verified.

5. Resolve modules with no Drupal 11 release

For each blocker you have four routes: update to a newer release, apply a community compatibility patch from the project's issue queue, replace the module with a maintained alternative, or write the patch yourself and offer it upstream. Composer can tell you exactly what is holding the version constraint:

composer why-not drupal/core 11.4.0

6. Move core to 11

composer require drupal/core-recommended:^11.4 drupal/core-composer-scaffold:^11.4 drupal/core-project-message:^11.4 --update-with-all-dependencies
drush updatedb -y && drush cache:rebuild

You will also need PHP 8.3 or newer, Drush 13 and Composer 2.7 or newer, and a database that Drupal 11 supports (MySQL 8.0, MariaDB 10.6, PostgreSQL 16 or SQLite 3.45).

7. Test before you deploy

Run your automated tests, then walk the critical paths by hand: login, content editing, any checkout or form that makes money, search, and anything integrated with an outside service. Keep the database backup and the Drupal 10 codebase tagged so rollback is a single deploy.

What usually goes wrong

  • CKEditor 4 still in use. Drupal 10 already moved editors to CKEditor 5. Sites with old text formats or custom CKEditor plugins need that migration done before Drupal 11.
  • One abandoned module blocks everything. Composer will refuse the core update until every package allows Drupal 11. Find these in step 2, not at deploy time.
  • Custom themes built on removed base themes. These need a real fix, not a patch.
  • Waiting until December. Every agency and freelancer has the same deadline. Capacity gets scarce and quotes rise as the date approaches, so the cheapest week to start is this one.

Decision checklist

  1. Is your site on Drupal 10.3 or later? If not, that catch-up comes first.
  2. Run Upgrade Status or the scanner. How many projects have no Drupal 11 release?
  3. Do you have custom modules or themes? How large?
  4. Is there a test suite or a staging site you trust?
  5. Can your team finish before December 9, with margin for review? If not, buy it or buy time with a written extended-support commitment.
