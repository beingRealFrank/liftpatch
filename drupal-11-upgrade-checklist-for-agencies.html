Drupal 11 upgrade checklist for agencies

With Drupal 10 security support ending on December 9, 2026, an agency with 20 client sites has a capacity problem more than a technical one. This checklist turns the work into a repeatable process.

1. Triage every site in one afternoon

  • Export each site's composer.lock. Scan it with the free scanner (it runs in the browser) or run Upgrade Status.
  • Record for each site: core version, PHP version, number of contrib modules, modules with no Drupal 11 release, custom code size, test coverage.
  • Sort into three bins: easy (all modules ready), medium (a few blockers), hard (abandoned modules, custom themes on removed base themes, no tests).

2. Contact clients on the date, not the technology

Tell clients that security fixes for their version stop on December 9, 2026, what it costs to move, and what happens if they don't. Get approval and repository access early; waiting on access is what usually delays upgrades.

3. Do it in two releases per site

  1. Release one: move to Drupal 10.6, update contrib to versions that support both 10 and 11, switch editors and removed core modules. Deploy. This is low risk.
  2. Release two: move core to 11.4 or later. Resolve any Composer blockers, then deploy.

4. Batch the easy sites

For the easy bin, use the same branch naming, PR template and deploy runbook for every site. A checklist per site beats custom planning each time.

5. Test and keep a rollback

Run each site's tests, walk the money paths by hand, tag the Drupal 10 code and keep a database backup so rollback is one deploy.
